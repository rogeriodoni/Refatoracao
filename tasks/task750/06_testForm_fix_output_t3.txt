Fixed. Root cause: `RestaurarColunaSelecao` sets `Column11.CurrentControl = "chk_4c_Selec"` right after `ControlSource = "CrSigMvCcr.Seleciona"`. This method runs during `InicializarForm` (via `ConfigurarPaginaHist`) while `CrSigMvCcr` is still the empty placeholder cursor (0 rows, `SET NULL ON` wrapped its `CREATE CURSOR`). With zero records there's no current row at all, so *any* field read returns `.NULL.` ÔÇö regardless of the `Seleciona N(1) NOT NULL` declaration, which only constrains what gets stored, not what's returned when there's no row. Binding that `.NULL.` into a numeric `CheckBox.Value` is exactly what throws `"Error with CHK_4C_SELEC - Value : Data type mismatch"`, aborting `Init` and making `CREATEOBJECT` return `.F.`.

The `TextBox` columns (1ÔÇô10) tolerate this fine since `TextBox.Value` adapts to the bound type/absence; `CheckBox.Value` does not.

Fix: guard the `CurrentControl` assignment with `IF USED("CrSigMvCcr") AND RECCOUNT("CrSigMvCcr") > 0`, skipping it while the cursor is empty. The later calls to `RestaurarColunaSelecao` (in `ExecutarConsultaSaldo`, already inside `IF RECCOUNT() > 0`, and in `CmbConciliaHistChange` after a real query) correctly re-bind the checkbox once real rows exist ÔÇö this also incidentally guards `CmbConciliaHistChange` against the same crash if a filter yields zero rows.

No business logic, schema, or naming conventions were touched ÔÇö only the one `IF` guard added in `Formsigopind.prg`.
