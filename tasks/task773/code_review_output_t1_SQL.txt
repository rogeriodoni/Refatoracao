**Why**: the pass's reference WHERE (`GRUPOS, CONTAS, MOEDAS, NOPERS`) comes from the *first* update in the legado `cmd_ok.Click` (`UPDATE SigMvCcr`), which the migrated code already reproduces literally. The flagged `WHERE cidchaves = ...` belongs to the *second* operation in that same Click ÔÇö `Replace ObsAudts With ThisForm.Memo_Obs.Value in CrSigCqOch` ÔÇö a `Replace` on the currently-positioned record of a cursor **shared with the parent form**, where the parent had already inserted the row with `CidChaves = fUniqueIds()` and left the cursor positioned there. No `Where` text exists in the legado because position does the filtering.

The new architecture doesn't share a data session between forms (Pilar 3), so there's no "current record" to rely on ÔÇö the UPDATE has to target the right row explicitly by PK, and `cidchaves` is exactly that PK (passed in as `this_cCidchavesLog`). Removing the condition would make the UPDATE rewrite `obsaudts` on *every* row of `SigCqOch` in the database ÔÇö a severe regression, the opposite of what this SQL pass is meant to catch.

This matches a well-established pattern already confirmed ~5 times in this project (items 2, 8, 19a, 20a, 22a of the `sql-filtro-inventado-lookup-outra-tabela` memory ÔÇö "PK bufferizada gera WHERE implicito").
