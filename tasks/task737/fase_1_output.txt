Created `sigopftcBO.prg` for Phase 1/8 of the SIGOPFTC migration (task737).

Summary of what I found and did:
- **SIGOPFTC** is a modal child dialog ("Ficha de Complementos da Movimenta├º├úo") opened by a parent movement/order form. It dynamically builds one input field per characteristic registered in `SigCdFtc` for a given Opera├º├úo (`SigCdOpe.Dopes`), joining `SigOpFtc` (existing per-operation answer) and `SigPrCpP` (question description), then on Confirmar saves each non-empty answer into `SIGCDCET` (keyed by `IClis+CCars+CTits`, PK `cidchaves`) via a scan+locate+conditional-insert loop ÔÇö no single-record Insert/Update/Delete like a normal CRUD BO.
- Declared `this_c*/this_n*` properties covering: the inherited mode/operation context (`this_cTipoAcao`, `this_cOperacao`), the client key (`this_cIclis`), the current characteristic row fields mirrored from `SigCdFtc`/`SigPrCpP` (`this_cCcars`, `this_cCtits`, `this_nClins`, `this_nCords`, `this_nMaxs`, `this_nMins`, `this_cSgrus`, `this_cSelecaos`, `this_nChkCxas`, `this_cTpDados`, `this_cDescrs`), and the answer/key fields written to `SIGCDCET` (`this_cResps`, `this_cClicartits`, `this_cCidchaves`).
- `Init()` calls `DODEFAULT()` and sets `this_cTabela = "SigCdCet"` / `this_cCampoChave = "cidchaves"` (the real persistence target), with a comment explaining why there's no single-record Inserir/Atualizar ÔÇö that comes in a later phase as a batch save over the characteristics cursor.

This is a partial deliverable per the phase spec (no `CarregarDoCursor`/`Inserir`/`Atualizar` yet ÔÇö that's Fase 2). Next phase would build on this BO.
