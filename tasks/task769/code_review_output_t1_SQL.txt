I investigated the `SQL-FILTRO-INVENTADO` finding for column `DOPPS` in `FormSigOpMpn.prg`/`SigOpMpnBO.prg` and it's a **false positive** ÔÇö I did not change the code.

**Why**: `DOPPS` only appears in a `WHERE` via `ExecutarCursorQuery("SigCdOpd", "cursor_4c_LocalOpd", "Dopps", valor, campos)` inside `CarregarNivel`, which builds `SELECT ... FROM SigCdOpd WHERE Dopps = valor`. The method's own comment documents this as a literal transcription of the legacy code: `=Seek(TmpNens.Dopps, 'crSigCdOpd', 'Dopps')` ÔÇö the legacy does a client-side `SEEK` on a pre-loaded, index-tagged cursor (`crSigCdOpd`), never a textual SQL `WHERE`. That's why the pass's dump-text extractor never captured `Dopps` as a legitimate original filter column, even though it's a faithful translation. The twin BO (`SigOpMpdBO.prg`) confirms the same helper call corresponds directly to the legacy framework call `CursorQuery('SigCdOpd','LocalOpp','Dopps', ...)`.

Removing the filter would make `ExecutarCursorQuery` return an arbitrary row of `SigCdOpd` instead of the matching level record, breaking `this_cNivelSubn`/`this_nSepPedras`/`this_nCompAgrus` and the button-enabling logic downstream.

This is the same documented false-positive family (SQLEXEC-with-WHERE Ôëí legacy `Seek()` over a pre-loaded cursor) seen in ~24 prior occurrences ÔÇö I logged this as the 25th occurrence in memory for future reference. No file changes were made for this pass.
