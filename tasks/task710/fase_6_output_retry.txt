## Two defects the probe caught

I couldn't instantiate the real form (SQL Server 192.168.200.10 is unreachable here, so `CarregarProduto` fails), so I probed via a subclass that replaces only the SQL load ÔÇö exercising the real `Configurar*`/`BINDEVENT` paths. All 10 checks pass, no dialogs. It surfaced:

1. **`SigOpCpoBO.AplicarFiltroTipo` had a latent Fase-2 bug I fixed.** `SET FILTER TO Tipos == THIS.this_cTipoSelecionado` stores the expression as *text* and re-evaluates it per record access, resolving `THIS` against whatever object is active then. Measured (`automation/MedirSetFilterThis.prg`): from inside the BO ÔåÆ OK; from another object ÔåÆ `Property THIS_CTIPOSELECIONADO is not found`; **from outside any object ÔåÆ VFP silently drops the filter** (`FILTER()` empty). Since the Grid repaints outside any method, the type filter would have shown all types with no error on screen. Now the value goes in as a literal, which works in all three contexts.

2. **A total that looks wrong but is faithful** ÔÇö worth knowing before someone "fixes" it. Measured (`automation/MedirSelectComSetFilter.prg`): VFP's local SQL `SELECT` *ignores* `SET FILTER` (100) while `SCAN`/`COUNT` respect it (90). The legacy `atuatotas` uses the SQL form, so the footer total covers the **whole** composition, not the filtered type. Our BO matches; I documented it in `AtualizarTotais` so it isn't converted to `SCAN` later, which would silently change a number the user sees.
