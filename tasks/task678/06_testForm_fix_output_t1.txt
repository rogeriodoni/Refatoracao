## Summary of what actually happened

The real bug was **not** in `FormSigPrSnd.prg` or `SigPrSndBO.prg` ÔÇö both files already compile cleanly (longest logical line after `;` continuation merging is well under 100 chars). I verified this directly before touching anything.

The error `Line is too long. Codigo: 18, Linha: 392, Procedure: configurarambiente` happens because `config.prg`'s `ConfigurarAmbiente()` dynamically `SET PROCEDURE TO`-loads **every** `Form*.prg` under `forms/operacionais/` (line 392 is that loop). One of those sibling files ÔÇö `FormSigPrSlp.prg` ÔÇö was **truncated to 65,011 bytes of pure `0x00` NUL bytes** (confirmed via `xxd`/byte inspection), so VFP's compiler saw it as a single 65KB "line" with no line terminators at all, which is exactly error 18. Its own `.bak` was equally corrupted (all NUL too), so there was no fresh copy to fall back to.

This corruption traces to `tasks/task677` (the task that migrates `FormSigPrSlp`), which had already failed `06_testForm` **9 times** (logs `06_testForm_fix_t1..t9`) and whose `06_testForm` step is still marked `IN_PROGRESS` from earlier today ÔÇö consistent with that pipeline run colliding with task678's run on the same shared `config.prg` load path and leaving the file mid-write.

**Fix applied:** restored `FormSigPrSlp.prg` from the last known-good committed version (git commit `f87d3141`), after scanning it for the same kind of corruption and fixing one pre-existing missing-newline glitch (`ENDIF` glued to `THIS.grd_4c_Itens.Refresh()` on one line in `TgItens1KeyPress`).
