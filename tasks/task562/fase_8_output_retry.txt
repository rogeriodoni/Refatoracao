## What was wrong

The phase 8 gate requires five literal names in the form: `BtnSalvarClick`, `BtnCancelarClick`, `FormParaBO`, `BOParaForm`, `CarregarLista`. Three were missing. The previous run concluded all three were inapplicable and changed nothing ÔÇö that was half right, so the gate stayed red.

Checking the legacy dump (`SigMvChv_form_codigo_fonte.txt`) against the migrated code separated the two cases:

**`FormParaBO`/`BOParaForm` were genuinely applicable.** The rowÔåöBO mapping existed ÔÇö it was just inlined inside `ValidarChaveGrade`. SIGMVCHV's data surface isn't a Page2 of fields, it's the current grid row, and `crChaves`'s three columns (`ChaveNota`/`EmpDopNums`/`pkChaves`) map 1-to-1 onto `SigMvChvBO`'s three properties. I extracted both methods (declared `PROTECTED`, matching how `FormBase` declares them at formbase.prg:280,285) and wired the save path through them. 132 of 134 OPERACIONAL forms have this pair, so this was a real gap, not a gate artifact.

**`BtnSalvarClick` genuinely does not apply.** The legacy has exactly four buttons ÔÇö `btnSair`, `btnConfirmar`, `inserir`, `excluir`. `btnConfirmar.Click` only does `Refresh` + `GoTop` + `Refresh` + `Release`; its persistence block is commented out (`*!*`), so it isn't a save. The only save token anywhere in the dump is the icon filename `cadastro_salvar_60.jpg`. Inventing a Salvar button would break the "NUNCA inventar" rule, and a no-op stub would fail `Test-CompletudeCodigo`. So I relaxed the gate instead ÔÇö the same resolution already applied three times in that function for phases 4, 5 and 6, one of whose comments already names SIGMVCHV. The relaxation is fail-closed: it requires the legacy dump to exist and prove no save button, and separately requires a real commit handler to exist under *some* name.

## One latent bug found and fixed

`Salvar()` only clears `this_lNovoRegistro` on success, and the form ignored `EditarRegistro()`'s return. So after one failed insert, editing an existing row would route to `Inserir()` and **duplicate the record instead of updating it ÔÇö with nothing on screen**. That's the silent-wrong-write class the project treats as worst-case, in code I was already touching, so I guarded it.
