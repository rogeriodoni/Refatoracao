All 6 findings in this pass are false positives ÔÇö same validator artifact documented 14 times before on this branch (`feedback_sql_filtro_inventado_comentario_prop_legado.md`). I verified each with `grep -n -i WHERE` on both files before touching anything:

- **CIDCHAVES**: PK-based `WHERE cidchaves = ...` in `BO.Atualizar()` (item) and the form's parcela-UPDATE ÔÇö required so the UPDATE doesn't hit every row in `SigMvOrc`/`SigMvOrp`.
- **DOPES / CEMPS**: `WHERE Dopes =` (SigCdOpe, SigOpCdd) and `WHERE Cemps =` (SigCdEmp) in `CarregarConfiguracao()` ÔÇö this dialog's own equivalent of the legacy's `CursorQuery`/`AddCursor` calls, which the parent form used to pre-load via a **shared DataSession** (`Lparameters poForm, pnDatSes`). This migrated dialog deliberately uses its own standalone cursors instead (documented in the file header), so it has to filter explicitly.
- **EMPS / NUMES**: `WHERE emps =`/`numes =` in `CarregarItens()`, `CarregarParcelas()`, and `CarregarConfiguracao()` (SigMvCab) ÔÇö same reason: without this filter the grids would load items/parcels from every budget across every company, not just the current one.
- **NITEM**: never a WHERE column at all ÔÇö it's `AS nitem` (a `COUNT(1)` alias) in `SELECT COUNT(1) AS nitem FROM ... WHERE citem2/citem3 = ...`. The real filter columns (`citem2`, `citem3`) are already in the reference list; the extractor just grabbed the alias.

Removing any of these would introduce the exact regression this rule exists to prevent (mass-update by missing PK filter, or loading the whole table instead of the current movement). No code changes made; I appended this as a 15th documented occurrence in memory so future passes on this pattern don't need to re-derive it.
