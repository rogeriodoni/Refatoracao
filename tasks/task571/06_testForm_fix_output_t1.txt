Fixed. Confirmed via grep that all remaining `txt_4c_Grupo`/`txt_4c_Conta`/`txt_4c_Dconta`/`txt_4c_Cpf` references now correctly belong only to the Destino block and the cheque panel (`cnt_4c__Chq`), which legitimately use those unsuffixed names.

**Root cause:** In `ConfigurarCamposIdentifica`, the Responsavel/Vendedor/Origem account blocks create their TextBoxes with numbered suffixes (`txt_4c_grupo2/3/4`, `txt_4c_conta2/3/4`, `txt_4c_dconta2/3/4`, `txt_4c_cpf2/3/4`) to avoid name collisions with the Destino block ÔÇö but the `BINDEVENT` calls right after creation, plus the paired `Grp*/Cta*/Dct*/Cpf*RespKeyPress/VendKeyPress/OrigKeyPress` handlers, still referenced the unsuffixed names. Since `BINDEVENT`'s arguments are evaluated immediately, `Property TXT_4C_GRUPO is not found` fired the moment `InicializarForm` reached the Responsavel block, aborting `CREATEOBJECT`.

**Fix:** corrected the 3 `BINDEVENT` blocks and the 12 corresponding handler methods to reference the actual suffixed control names (`*2` for Responsavel, `*3` for Vendedor, `*4` for Origem). Destino's handlers were already correct and untouched.

Note: `AbrirCadastroConta`/`BtnCadastrosOrigemClick` (around line 6925) has the same suffix mismatch when called for the Origem block, but that's a separate click-time path unrelated to the reported `InicializarForm` crash, so I left it out of scope for this fix.
