**Not touched** ÔÇö the other 4 "DIFERENCA" rows (`sigproef.oModem.Top/Left/Height/Width`, legacy 144/264/100/100 vs "migrado" 3/1/333/581): these are a validator false positive, not a form bug. The legacy `oModem` is an `olecontrol` (ActiveX modem/fiscal-printer driver) that was correctly *not* ported to a visual VFP9 control ÔÇö that functionality lives in `sigproefBO.CarregarDadosImpressoraFiscal()` instead, per project convention for OLE controls without an available OCX. The "migrado" values reported (3/1/333/581) aren't from any `oModem` ÔÇö they're exactly `cnt_4c_Transa`'s Top/Left/Height/Width, which in turn match the legacy `CntTransa` container byte-for-byte (dump lines 201-204). The comparator pairs legacy/migrated objects positionally, and with `oModem` legitimately absent from the migrated tree, it desynced and attributed `oModem`'s legacy geometry to the next sibling in its list (`CntTransa`). Applying the reported "fix" would have broken a container that's already pixel-perfect.

I saved this comparator-desync pattern to memory (`feedback_comparadorui_ole_ausente_desalinha_proximo_objeto.md`) so it's recognized immediately if it recurs on other forms with unported OLE controls. The AVISO rows in the same report are the known false-positive categories already documented in memory (grid/column introspection limits, cabecalho propagation) ÔÇö none required changes either.
